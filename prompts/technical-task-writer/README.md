# Technical Task Writer

**Версия:** v1.0  
**Владелец:** Олег Махалов  
**Теги:** development, documentation, technical-task, prompt-engineering  
**Цель:** подготовка структурированного технического задания для разработчика на основе описания новой функциональности.

## Шаблон

```text
Ты — опытный системный аналитик и технический писатель.

Task

Подготовь техническое задание для реализации новой функциональности.

Context

Документ предназначен для передачи разработчику. Техническое задание должно быть понятным, логичным и достаточным для реализации без дополнительных уточнений, если входных данных достаточно.

Input

Проект:
{PROJECT}

Название функции:
{FEATURE}

Описание задачи:
{DESCRIPTION}

Бизнес-цель:
{GOAL}

Требования:
{REQUIREMENTS}

Ограничения:
{CONSTRAINTS}

Output

Подготовь техническое задание следующей структуры:

1. Цель
2. Описание задачи
3. Пользовательский сценарий
4. Изменения интерфейса
5. Изменения backend
6. Изменения базы данных
7. API и интеграции
8. Возможные исключения и пограничные случаи
9. Критерии готовности
10. План тестирования

Правила:

- используй только сведения из входных данных;
- не придумывай отсутствующие требования;
- отделяй обязательные требования от предположений;
- если данных недостаточно, перечисли вопросы, требующие уточнения;
- формулируй критерии готовности так, чтобы их можно было проверить.

Перед завершением ответа проверь:

- все необходимые разделы присутствуют;
- требования не противоречат друг другу;
- требования не дублируются;
- критерии готовности проверяемы;
- план тестирования соответствует требованиям.
```

## Пример входа

```text
PROJECT:
Умное меню

FEATURE:
Проверка и заказ домена

DESCRIPTION:
Администратор клуба вводит желаемое доменное имя, получает варианты и видит статус каждого варианта. Свободный домен можно выбрать и отправить заявку на регистрацию.

GOAL:
Упростить подключение собственного домена к странице клуба.

REQUIREMENTS:
- предложить несколько вариантов доменного имени;
- проверить доступность каждого варианта;
- показать свободные и занятые варианты;
- разрешить выбрать свободный вариант;
- отправить заявку администратору сервиса;
- после подтверждения сообщить пользователю о регистрации и настройке домена.

CONSTRAINTS:
- домен регистрирует администратор сервиса;
- пользователь не оплачивает домен напрямую;
- привязанный домен должен сохраняться в адресной строке.
```

## Пример выхода

```text
1. Цель

Реализовать для администратора клуба проверку доступности доменных имён и отправку заявки на регистрацию выбранного свободного домена.

2. Описание задачи

В разделе управления клубом необходимо добавить форму ввода доменного имени, автоматическую генерацию вариантов и отображение статуса каждого варианта.

3. Пользовательский сценарий

Администратор вводит название, просматривает предложенные варианты, выбирает свободный домен и отправляет заявку. После обработки заявки получает уведомление о регистрации и настройке домена.

4. Изменения интерфейса

Добавить поле ввода, список вариантов со статусами «Свободен» и «Занят», кнопку выбора свободного варианта и кнопку отправки заявки.

5. Изменения backend

Реализовать проверку доступности доменов, сохранение заявок и изменение статуса заявки администратором.

6. Изменения базы данных

Добавить сущность заявки на домен с полями клуба, пользователя, доменного имени, статуса и дат создания и обработки.

7. API и интеграции

Добавить методы получения вариантов, проверки доступности, создания заявки и подтверждения регистрации.

8. Возможные исключения и пограничные случаи

Недопустимое имя, повторная заявка, изменение доступности домена до регистрации, ошибка внешнего сервиса проверки.

9. Критерии готовности

Все варианты получают статус; заявку можно отправить только для свободного домена; статус заявки сохраняется; после подтверждения пользователь получает уведомление; домен открывает страницу клуба и остаётся в адресной строке.

10. План тестирования

Проверить корректные и некорректные имена, свободные и занятые варианты, повторные заявки, ошибки внешнего сервиса, подтверждение заявки и открытие страницы клуба по собственному домену.
```

## Тест-кейсы

### Тест-кейс 1. Полные входные данные

**Вход:** заполнены все переменные.  
**Ожидаемый результат:** сформированы все 10 разделов; нет вопросов на уточнение; критерии готовности проверяемы.

### Тест-кейс 2. Недостаточно данных

**Вход:** указаны только проект, название функции и краткое описание.  
**Ожидаемый результат:** модель не придумывает недостающие требования и отдельно перечисляет вопросы для уточнения.

### Тест-кейс 3. Противоречивые требования

**Вход:** в требованиях указано автоматическое подтверждение, а в ограничениях — обязательное ручное подтверждение.  
**Ожидаемый результат:** модель отмечает противоречие и просит определить корректный вариант до подготовки окончательного технического задания.
